## 四、「红转绿」能力边界（基于 `src/api/recover.rs` 实现，非商品描述）

链路（文件头注释原文）：

```
违规自查(cheat) → 记录列表 → 逐条读详情拿 reasonList
→ 用「原记录的开始时刻」重新生成合规轨迹并覆盖提交 → 复查是否变达标
```

成立依据（代码注释自述）：`POST /api/v70260/runnings/save/record` 对同一天同一 `sportType` 没有去重锁，新提交顶替旧记录（证据：商品截图里 1.72km 记录修复后变 1.68km）。

| 能力 | 可做 | 说明 |
|---|---|---|
| 只读诊断（禁跑状态 / 违规榜 / 异常记录 + 原因） | ✅ | 默认行为，无 `--yes` 时一个请求都不发 |
| 单条记录「变绿」 | ✅ | 用原 `startTime` 重跑并覆盖 |
| 批量一键全绿 | ⚠️ 不做 | 同日多条同时改写 → 「记录被篡改」强特征 |
| 解除「禁跑」处罚 | ❌ | 台账在 `cheatlist` 的 self 段，recover 改的是记录；只能申诉或等到期 |

三条风险（必须随功能一起告知用户）：
1. 覆盖假设的唯一证据是一张商品截图，**无抓包佐证**；
2. 假设不成立 → 同一天产生两条记录，比原来严重；
3. 对已被标记 20 条的账号反复覆盖，本身会形成「同一天 distance/startTime 多次变化」的痕迹。

实现现状：`src/api/recover.rs`（490+ 行）+ CLI `nekosportsworldtool recover [--yes] [--verify] [--only rrid] [--limit n] [--dist km] [--pace 秒/km] [--force]`（`cli/cmds.rs:785`，命令表 `cli/mod.rs:36`）。**`src/ui/` 零引用** —— 这就是用户在 App 里找不到它的原因。0.9.0 的 `t5` 负责加入口（默认只读、单条、不做批量）。
